# Day 11 — Profile a Slow Endpoint

## Overview

This task adds a deliberately slow performance endpoint to the existing Week 5 `QuotesAPI` and profiles it under load.

The endpoint intentionally demonstrates two database performance problems:

1. **N+1 queries** when loading quotes for each author.
2. **Missing index** on the `Author` column.

The goal of this task is to profile and identify the problems by collecting:

- p50 and p99 latency under load
- SQL generated by EF Core
- SQLite execution plan

> **Note:** The task focuses on profiling the slow endpoint. Fixing the identified problems is not required for this task.

---

## Objective

The objective was to:

- Reuse the existing Week 5 `QuotesAPI`.
- Add a deliberately slow endpoint.
- Create enough test data to make the performance issue measurable.
- Introduce an N+1 query pattern.
- Leave the `Author` column without an index.
- Run the endpoint under load using k6.
- Capture baseline p50/p99 latency.
- Inspect the SQL generated by EF Core.
- Inspect the SQLite execution plan.
- Identify the two biggest performance problems.

## Deliberately Slow Endpoint

### Endpoint

```http
GET /api/performance/author-quotes
```

### N+1 implementation

The endpoint first retrieves the distinct authors:

```csharp
var authors = await db.Quotes
    .Where(q => !q.IsDeleted)
    .Select(q => q.Author)
    .Distinct()
    .ToListAsync(cancellationToken);
```

It then executes another query for every author:

```csharp
foreach (var author in authors)
{
    var quotes = await db.Quotes
        .Where(q =>
            !q.IsDeleted &&
            q.Author == author)
        .Select(q => new
        {
            q.Id,
            q.Author,
            q.Text
        })
        .ToListAsync(cancellationToken);
}
```

This creates the N+1 pattern.

With approximately 100 authors:

```text
1 query  → retrieve authors
100 queries → retrieve quotes for each author
-----------------------------------------------
≈ 101 database queries
```

# Offending SQL

The first query retrieves the distinct authors:

```sql
SELECT DISTINCT "q"."Author"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted");
```

The endpoint then executes this query once for every author:

```sql
SELECT "q"."Id", "q"."Author", "q"."Text"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted")
  AND "q"."Author" = @author;
```

The repeated author-specific query demonstrates the N+1 behavior.

Conceptually, the database receives:

```text
SELECT authors

SELECT quotes WHERE Author = Author 1
SELECT quotes WHERE Author = Author 2
SELECT quotes WHERE Author = Author 3
...
SELECT quotes WHERE Author = Author 100
```

# Execution Plan

SQLite's `EXPLAIN QUERY PLAN` was used to inspect the quote lookup.

```sql
EXPLAIN QUERY PLAN
SELECT "q"."Id", "q"."Author", "q"."Text"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted")
  AND "q"."Author" = 'Performance Author 1';
```

### Baseline result

```text
SCAN q
```

The temporary endpoint:

```http
GET /api/performance/query-plan
```

returned:

```json
[
  {
    "id": 2,
    "parent": 0,
    "notUsed": 216,
    "detail": "SCAN q"
  }
]
```

### Meaning

`SCAN q` indicates that SQLite is scanning the `Quotes` table for the author lookup instead of using an index.

There is no useful index on:

```text
Quotes.Author
```

for this query.

---

# Two Biggest Problems

## 1. N+1 Query Problem

The endpoint first retrieves the authors and then performs a separate database query for every author.

Instead of one database query, the endpoint performs approximately:

```text
1 + N queries
```

With around 100 authors:

```text
≈ 101 database queries
```

This creates unnecessary database round trips and contributes to the endpoint's latency.

---

## 2. Missing Index

The quote lookup filters using:

```sql
WHERE "q"."Author" = @author
```

but there is no index on `Quotes.Author`.

The SQLite execution plan confirms this:

```text
SCAN q
```

This means SQLite scans the table rather than performing an indexed lookup.

# Key Learning

An API can return the correct response while still performing poorly at the database level.

The load test showed the latency impact, the EF Core SQL logs exposed the N+1 query pattern, and the SQLite execution plan exposed the missing index.

Using all three pieces of evidence makes it possible to identify the actual causes of a slow endpoint instead of relying only on the API response time.
