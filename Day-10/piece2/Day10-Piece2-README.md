# Day 10 — Piece 2: EF Core SQL Generation, Projection & Client Evaluation

## Overview

This exercise demonstrates how Entity Framework Core translates LINQ queries into SQL and how query shape affects the SQL sent to the database.

The exercise covers three areas:

1. Inspecting SQL generated by EF Core using `LogTo`.
2. Comparing a full entity query with a DTO projection.
3. Identifying an unsupported C# method inside an EF Core query and replacing it with a SQL-translatable expression.

The project uses **ASP.NET Core, EF Core and SQLite**.

---

## Objectives

By completing this exercise, I demonstrated that I can:

- Inspect SQL generated by Entity Framework Core.
- Understand which entity columns EF Core retrieves.
- Use `Select()` projection to fetch only required columns.
- Create a DTO for read-only query results.
- Recognize expressions that EF Core cannot translate to SQL.
- Fix a non-translatable query by using a SQL-translatable expression.
- Use development-only SQL and sensitive-data logging safely.

# 1. EF Core SQL Logging

SQL logging was enabled so that the SQL generated by EF Core could be inspected directly in the application console.

```csharp
builder.Services.AddDbContext<QuotesDbContext>(options =>
{
    options.UseSqlite(
        builder.Configuration.GetConnectionString("DefaultConnection"));

    options.LogTo(Console.WriteLine);

    options.EnableSensitiveDataLogging();
});
```

### Why this was used

`LogTo(Console.WriteLine)` prints EF Core activity and generated SQL to the console.

`EnableSensitiveDataLogging()` allows parameter values and additional query information to appear in development logs.

Sensitive-data logging should **not be enabled in production**, because log output can contain application data.

The application confirmed that EF Core was initialized with SQLite and sensitive-data logging enabled.

# 2. Original Full-Entity Query

The first query loads complete `Quote` entities.

```csharp
var fullEntityQuotes = await db.Quotes
    .Where(q => !q.IsDeleted)
    .OrderBy(q => q.Id)
    .Take(10)
    .ToListAsync();
```

### What this query does

The query:

1. Reads from the `Quotes` table.
2. Filters out deleted quotes.
3. Orders the results by `Id`.
4. Takes 10 records.
5. Materializes complete `Quote` entities.

Because the result is a `Quote` entity, EF Core retrieves all mapped columns required to create that entity.

---

## Actual SQL Generated by EF Core

```sql
SELECT "q"."Id", "q"."Author", "q"."IsDeleted", "q"."Text"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted")
ORDER BY "q"."Id"
LIMIT @p
```

This SQL was captured directly from the EF Core console output.

The query returned:

```json
{
  "rows": 10
}
```

# 3. DTO Projection

Instead of loading the complete entity, the query was rewritten using a DTO projection.

## QuoteDto

```csharp
namespace QuotesApi.Models;

public sealed class QuoteDto
{
    public int Id { get; init; }

    public string Author { get; init; } = string.Empty;

    public string Text { get; init; } = string.Empty;
}
```

The DTO contains only the data required by the read operation.

---

## Projected Query

```csharp
var projectedQuotes = await db.Quotes
    .Where(q => !q.IsDeleted)
    .OrderBy(q => q.Id)
    .Select(q => new QuoteDto
    {
        Id = q.Id,
        Author = q.Author,
        Text = q.Text
    })
    .Take(10)
    .ToListAsync();
```

### Why projection is better for this read operation

The application does not need `IsDeleted` in the returned data.

The projection tells EF Core exactly which properties are required:

```text
Id
Author
Text
```

Therefore EF Core can generate a smaller `SELECT` statement.

---

## Actual Lean SQL Generated by EF Core

```sql
SELECT "q"."Id", "q"."Author", "q"."Text"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted")
ORDER BY "q"."Id"
LIMIT @p
```

The projected query also returned:

```json
{
  "rows": 10
}
```

# 4. Full Entity vs Projection

| Aspect | Full Entity | DTO Projection |
|---|---|---|
| Result type | `Quote` | `QuoteDto` |
| Columns selected | `Id`, `Author`, `IsDeleted`, `Text` | `Id`, `Author`, `Text` |
| `IsDeleted` returned | Yes | No |
| Complete entity materialized | Yes | No |
| Suitable for read-only response | Sometimes | Yes |
| SQL column selection | Wider | Leaner |

### Generated SQL difference

#### Full entity

```sql
SELECT "q"."Id", "q"."Author", "q"."IsDeleted", "q"."Text"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted")
ORDER BY "q"."Id"
LIMIT @p
```

#### DTO projection

```sql
SELECT "q"."Id", "q"."Author", "q"."Text"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted")
ORDER BY "q"."Id"
LIMIT @p
```

The DTO projection removes the unnecessary `IsDeleted` column from the result set.

This becomes more important with larger entities containing many columns, especially large text or binary fields.

# 5. Tracking Behavior During Full Entity Query

The EF Core logs also showed that the full entity query started tracking the returned `Quote` entities.

Example log:

```text
StartedTracking 'Quote' entity
```

This happens because normal EF Core entity queries use the default tracking behavior.

The DTO projection does not materialize `Quote` entities. It creates `QuoteDto` objects directly from the selected columns.

This reinforces the distinction between:

- Loading entities when entity behavior is required.
- Projecting DTOs when only read data is required.

# 6. Accidental Client-Side Evaluation

The exercise also tested a custom C# method inside the EF Core query.

```csharp
var quotes = await db.Quotes
    .Where(q => QuoteQueryHelpers.IsLongAuthor(q.Author))
    .ToListAsync();
```

The helper method was:

```csharp
public static class QuoteQueryHelpers
{
    public static bool IsLongAuthor(string author)
    {
        return author.Length > 10;
    }
}
```

## Problem

`IsLongAuthor()` is an application-defined C# method.

EF Core cannot translate arbitrary application methods into SQL.

Therefore this expression cannot be translated into a database query:

```csharp
QuoteQueryHelpers.IsLongAuthor(q.Author)
```

Modern EF Core reports a query translation failure instead of silently evaluating the `Where` condition on the client.

This is important because moving filtering into application memory can result in unnecessary rows being loaded from the database.

---

# 7. Fixed Client-Evaluation Query

The custom method was replaced with an expression that EF Core can translate.

### Problematic version

```csharp
var quotes = await db.Quotes
    .Where(q => QuoteQueryHelpers.IsLongAuthor(q.Author))
    .ToListAsync();
```

### Fixed version

```csharp
var quotes = await db.Quotes
    .Where(q => q.Author.Length > 10)
    .ToListAsync();
```

The fixed expression uses a property operation that the SQLite provider can translate into SQL.

The filtering can therefore be performed by the database instead of application code.

# 10. Key Findings

### Finding 1 — EF Core generates SQL from LINQ

The LINQ query:

```csharp
db.Quotes
    .Where(q => !q.IsDeleted)
    .OrderBy(q => q.Id)
    .Take(10)
```

was translated into SQL containing:

```sql
WHERE NOT ("q"."IsDeleted")
ORDER BY "q"."Id"
LIMIT @p
```

---

### Finding 2 — Projection controls selected columns

The full entity query selected:

```text
Id
Author
IsDeleted
Text
```

The DTO projection selected:

```text
Id
Author
Text
```

Therefore projection avoids retrieving columns that the application does not need.

---

### Finding 3 — Projection is useful for read paths

For API read operations where the application only needs a subset of an entity, DTO projection is preferable to loading the complete entity.

---

### Finding 4 — Unsupported C# methods should not be used inside database filters

This:

```csharp
.Where(q => QuoteQueryHelpers.IsLongAuthor(q.Author))
```

cannot be translated by EF Core.

The database should perform filtering whenever possible.

---

### Finding 5 — Use translatable expressions

This:

```csharp
.Where(q => q.Author.Length > 10)
```

can be translated by EF Core and allows the database to perform the filtering.

# 11. Engineering Takeaways

## Use full entities when:

- The complete entity is required.
- The entity will be modified and saved.
- Entity tracking or domain behavior is required.

## Use projection when:

- The operation is read-only.
- Only a subset of columns is required.
- The result is being returned through an API.
- Reducing database payload is useful.
- Loading full entities would be unnecessary.

## Avoid client-side filtering when:

- The dataset can be large.
- The filtering can be performed by SQL.
- The query would otherwise transfer unnecessary rows to the application.

# Conclusion

This exercise demonstrated how EF Core translates LINQ into SQL and why query shape matters.

A full entity query retrieves all mapped entity columns and materializes tracked entities. A DTO projection allows the application to request only the columns it needs, producing a leaner SQL query.

The client-evaluation test also showed why database queries should use expressions that EF Core can translate. Unsupported application methods can cause translation failures and, if client evaluation is explicitly introduced, can result in unnecessary data being loaded into application memory.

The main practical lesson is:

> **Shape the query for the data the application actually needs, and keep filtering and other database operations translatable to SQL.**
